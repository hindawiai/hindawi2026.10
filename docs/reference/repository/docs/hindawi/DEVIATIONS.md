# Where this repository deviates from legacy Hindawi

**The baseline.** Every comparison below is against hindawiai/chintamani, which is not Hindawi's source architecture. Hindawi
was released in 2004 and went through several iterations; Chintamani is a recent one, about four or five years old,
made for the Telugu implementation (hence its Telugu filters), whose Python Telugu went as far as a face-recognition
program in a notebook. A comparison with the 2004 releases, reconstructed in hindawiai/hindawi-legacy, has not
been made yet.

Legacy Hindawi is `hindawiai/chintamani` at 3ad8778. Its copy in `lang/hindawi/upstream/chintamani` is byte for
byte Chintamani, and `tests/fundamental.py` F1 checks that it stays so. Everything below differs from it. It is
recorded here and nothing in it has been changed.

## In the generated language cells (`lang/hindawi/languages/`, BUILD-0102)

1. **The cells exist at all.** Legacy Hindawi has Hindi only. The other 75 cells were generated.
2. **The Hindi cell is not Chintamani's Hindi.** Its `h2c.uhin` differs in 676 lines, has 325 rules against 323,
   and has lost the 2003 to 2006 copyright and GPL notice.
3. **Five languages carry Hindi's transducer.** Sanskrit, Marathi, Nepali, Awadhi and Bhojpuri have Hindi's
   transducer, byte for byte.
4. **Keywords are replaced inside longer words.** The cells have no rule for identifiers, so a keyword is
   replaced wherever it appears: `interval` becomes `<int>erval`, `printf` becomes `pr<int>f`. They also map the
   single letter `c` to `native`.
5. **Fifty-two cells' reverse transducers run the wrong way.** They map native to English instead of English to
   native, and some emit placeholders (`KW_IF`) rather than C.
6. **Seventeen languages have Latin keywords,** although most of them have scripts of their own. All 76 store a
   hand-made romanised column in `pipeline/language_params.json`.
7. **Some cells disagree with themselves.** In Bengali and Tamil, `c2h` and `h2c` use different words for the
   same keyword, so a program ingested through one does not compile through the other.
8. **The Makefiles skip the script filter.** Non-Devanagari cells' Makefiles feed their text straight to `uni2acii`,
   which reads Devanagari only.

## In the tools around them

9. **Grok's original `hindawicc`** sent every language through Hindi's `h2c`, bypassed Romenagri, and fell back to
   compiling the raw source. C11 rewrote it on the original chain.
10. **`pipeline/transliterate.py`** carries every script to Devanagari before h2c. Legacy Hindawi had script
    filters for Telugu and Urdu only (`fltr_*`).
11. **The script tables** (`tools/pushkalavati-compiler/vendor/romenagri/upstream/tables`) are headers only.
    Where they are empty, `transliterate.py` projects by Unicode name, as their headers say they do.
12. **BURP's ingestion path reads each cell's rules and applies them per token in Python,** outside literals,
    comments and `#include` names. It does not run the cells' flex lexers. That avoids deviation 4 without
    editing any cell. The compilation path still runs the lexers.

## Legacy behaviour, not deviations, recorded because they matter

- **Underscores.** Romenagri's `acii2cf` doubles every underscore in ASCII identifiers (`debug_putc` becomes
  `debug__putc`).
- **Assembly.** the original Hindawi assembly pair is not round-trip stable on its sample.
- **Format strings.** `c2h` localises format strings (`%d` becomes `%द`), and `gurucc` repairs only `%प`,
  `%भ` and `\न` on the way back.

## 17 October 2026: the compilation path back on the original pipeline, and the cells completed

- **The compilation path is the original pipeline again.** Grok's `pipeline/transliterate.py` is out of it. A source in
  another script now goes through a script filter in front of Romenagri, as the original drivers do: the original Hindawi
  `fltr_te_hi` (Telugu) and `fltr_ur_hi` (Urdu and the other Perso-Arabic scripts), and, for the other Brahmi scripts,
  filters of the same kind generated by Unicode name (`lang/hindawi/tools/script_filters.py`). Then fixuninum and
  Romenagri (`uni2acii`, `acii2cf`, `acii2uni`), then the language's `h2c`, then the original driver's repairs.
  Compilation therefore runs on the transliterated form. A script with no filter yet (Cyrillic, Hebrew, the CJK and
  Southeast Asian scripts, Latin) has no compilation path; it ingests and reads in full.
- **One addition the original did not need.** Chintamani's Perso-Arabic filter reads alef by its context, so a lexer's
  keyword is filtered both at the start of a line and after a space, and gets a rule for each form.
- **One addition kept, and switchable.** Names already in ASCII (`CONFIG_X`, `memcpy`) are held aside on the compilation
  path, because `acii2cf` doubles their underscores; Hindi programs of 2004 had no ASCII names, upstream code does.
- **The cells are complete from their own lexicons.** The delivered cells carried the same 28 rules in all eighteen
  files; `lang/hindawi/tools/complete_cells.py` regenerates each from the language's lexicon, in Chintamani's form, with
  a word rule so a keyword is never replaced inside a longer name. Every construct still without a word is listed in
  the cell's `STATUS.tsv`, and offered for review on `docs/hindawi/review.html`.

## 17 October 2026, later: nine languages completed, and native names made exact on the compilation path

Translating the GATE programs' names into Dari, Pashto, Urdu, Punjabi (Gurmukhi and Shahmukhi), Sindhi, Telugu,
Kannada and Sanskrit put native names through the compilation path at scale for the first time. Four things in the
original pipeline gave one name two C-level forms, or none; each is now handled, and each is recorded here.

- **Each native word is transliterated on its own.** Chintamani's Perso-Arabic filter reads a word-initial letter by
  what precedes it, so the same name came out one way after a space and another after a bracket, and the program did
  not link. The compilation path now sends each native word through the script filter and Romenagri separately, exactly
  as the cell's rules are built, so a word has one form wherever it stands. The text around the words never passes
  through the filter. Hindi output is unchanged (`tests/fundamental.py`, 12 checks).
- **Pashto and Sindhi letters are folded for the Urdu filter.** `fltr_ur_hi` does not know ټ ډ ړ ږ ښ ګ ڼ ې ۍ ځ څ or
  ڪ ڳ ڱ ڄ ٻ ڀ ٽ ٿ ڊ ڏ ڍ ڙ ڦ ڻ ڇ ڌ ۀ, and emitted control bytes for them. They are folded to the nearest Urdu letter
  before the filter (`script_filters.FOLD`), on the rules and the words alike. Two names that differ only in such a
  letter would share a C-level form; the source, the dictionary and ingestion keep them apart.
- **Romenagri's mid-word vowel marker is written `_`.** `acii2cf` marks a vowel-initial syllable inside a word with `^`,
  which no C identifier may contain. It is written `_`, as Romenagri itself writes a vowel at the start of a word, in
  the compiled rules and in the words alike (`hindawi_chain.cform`).
- **The cells' literal rules are the standard ones.** the original character-literal rule `\'("\\\'"|.*)*\'` is greedy:
  on a line with two character literals it swallows everything between them, keywords included, and its string rule
  excludes `^`. The generated cells use the standard patterns. Hindi keeps Chintamani's transducers as they are, so
  the greedy rule is still there for Hindi; it is a defect of the original, recorded rather than changed.
- **Gurmukhi signs under other Unicode names are mapped.** The generated Gurmukhi filter maps letters to Devanagari by
  Unicode name, and Gurmukhi names some signs differently (bindi and tippi for anusvara, the vowel signs EE and OO for
  E and O); those passed through raw and Romenagri emitted control bytes. They are now mapped by alias. Addak, which
  doubles the next consonant, has no Devanagari sign and is dropped on the compilation path, so two names differing
  only by addak share a C-level form; the source, the dictionary and ingestion keep them apart.
- **Short and long e and o are kept apart for the Dravidian scripts.** Mapping Kannada, Tamil and Malayalam to
  Devanagari by Unicode name put short e (ೆ) on Devanagari's e (े) and left long ee (ೇ), and likewise o and oo,
  unmapped, so Romenagri emitted control bytes. The generated filters now map short e and o to Devanagari's short e
  and o letters and signs (ऎ ॆ ऒ ॊ) and long ee and oo to its e and o, as ISCII does for the southern scripts.
  Telugu uses the original Hindawi filter and is unchanged.
- **One word, one construct, in each cell.** Some lexicons give two constructs the same word (Sanskrit लिख for both
  write and printf; صحيح for both int and true in the Perso-Arabic lexicons), and a cell built from them compiled
  every such word back to only one of the two. The generator now keeps each word with one construct: the same token in
  another case (FOR, for) counts as one construct; a token with a proposed word of its own takes that word; otherwise
  the better-sourced token keeps the word and the other is listed in the cell's `STATUS.tsv` as sharing it.

## 18 October 2026: stages shown, Python on the original path, whole words

- **The compilation path is shown stage by stage** (`hindawi_chain.stages()`): source, the script filter's Devanagari,
  the Romenagri form, and the host-language text. `to_c` is the last stage, so what is shown is what is compiled.
- **Python runs on the original path.** Chintamani's Makefile builds `h2py` through `uni2acii | acii2cf`, as it builds
  `h2c`; each language's `h2py` is now built and run the same way, so a name reaches Python in its Romenagri form, the
  form it has in C and in the binary. Hindi uses the original Hindawi `h2py`.
- **Whole words only.** Every generated forward transducer ends with a rule that passes a whole word through unchanged,
  so a keyword is never matched inside a longer name; a keyword of the same length still wins by coming first.
  the original Hindawi transducers for Hindi are unchanged and do not have this rule.
- **Known in Hindi, not changed:** the original greedy character-literal rule makes 2 of the 113 GATE C programs fail
  in Hindi (recursive_descent_parser.c, regex_matcher.c). It is task T-10.
